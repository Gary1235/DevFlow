# DevFlow 整體盤點與改善順序

日期：2026-10-23。範圍：目前 checkout 的啟動器、React 工作台、API、Worker、CLI 轉接、權限、驗證、恢復、審查與合併。

使用者實際故障發生在**另一台主機的 `npm run dev` 開發版**。本機預設開發版與桌面版資料庫沒有專案／任務／Run，因此本報告的缺陷來自程式碼檢查與本機測試，不能當成另一台主機個別事故的日誌鑑定。沒有修改執行邏輯或放寬權限。

## 結論

專案已有相當完整的工作台與狀態儲存能力，但距離無人看守的自動開發，主要缺口是：

1. 「檔案範圍授權」和「任意 Shell 程式的執行授權」不是同一件事；目前依賴有限的文字解析，正常工作也常落入人工確認。
2. 等待工具權限沒有完整的全域通知與排程處理；人沒看到時，單一 Worker 會一直被占住。
3. 驗證失敗大多直接結束，尚未有完整的診斷、修正、再驗證循環。
4. 自訂工作流程的續跑基底與審查門檻存在正確性缺陷，不能只靠新增解析白名單解決。

| `backend: dotnet build DevFlow.slnx --no-restore --verbosity minimal` | 通過，0 警告、0 錯誤，包含 Worker | 不是全新主機的 restore／部署驗證 |

後端首次沙箱執行也受到 Windows Service Control Manager 存取限制；桌面／啟動器首次受到 loopback 限制。這些與另一台主機的 DevFlow 權限請求不同，不能混為同一根因。本次沒有呼叫付費 AI 執行真實任務，也沒有建置安裝包。

## 優先修正：權限與可見性

### A1．開發版缺少背景工具核准通知（P1，已確認）

- `frontend/src/components/TaskPermissions.tsx:12` 只在指定任務／Run 的元件啟用時讀取確認。
- `frontend/src/hooks.ts:11` 在 `document.hidden` 時停止週期讀取。
- `frontend/src/components/ToolPermissions.tsx` 的兩分鐘提醒只是在頁面卡片上更新文字。
- 桌面版 `desktop/src/main.cjs:144`、`desktop/src/services.cjs:142` 也只依任務狀態變化通知，不追蹤工具確認 ID；工具確認時任務仍可維持 Running／Planning。

**影響：**切換到其他任務、其他網頁或縮小視窗，容易完全不知道正在等核准。使用者目前使用開發版，單改 Electron 通知無法解決。

**建議：**新增全域待處理 API，涵蓋任務與討論；顯示待確認數量、等待時間、阻塞原因。開發版提供使用者啟用的瀏覽器通知、標題提示與可選聲音，處理頁面背景節流；若要求關閉網頁後仍通知，另設常駐通知程序或適當的推播機制。通知以 request ID 去重，重啟後可重新提示尚未處理項目。不能靠背景分頁的一秒輪詢保證即時通知。

**驗收：**任務頁未開啟、切換分頁、回到前景、重新啟動，各情境都能看見待辦；同一請求不重複轟炸，點擊可直達確認。

### A2．無限等待占住唯一 Worker（P1，已確認）

`TaskPermissionPlanningRunner.Operation` 每 200ms 等待確認，沒有自身期限；`DevFlow.Worker/Program.cs:73` 逐一 await 規劃／實作。預設 ExecutionTimeoutSeconds 為 0。

**影響：**單一任務等待確認，後續所有 Worker 任務一起排隊；心跳仍可能顯示 Working，容易看成「AI 還在執行」。

**建議：**分開表示執行中、等待權限、等待規格回覆與失去活動；記錄阻塞起點。加入有界並行與每個 repository 的互斥，或持久化等待後安全讓出執行名額。需先設計 CLI 存活／重連語意，不能假裝已結束 CLI 可原地恢復。逾時策略由使用者選擇提醒／暫停／取消，不自動核准。

**驗收：**A 等待核准時，獨立專案的 B 可執行；重啟、取消、舊請求回覆不會重複執行工具。

### A3．解析能力與實際 CLI 指令形式不一致（P1，已確認）

- `CommandPermissionRisk.Policy.cs` 以自行實作的字串／token 邏輯處理有限的串接、管線與檔案操作。
- `PermissionTools.cs:29` 將 Claude Bash 標為 bash，其他 commandExecution／run_shell_command 標為 unknown。因此 Codex／Gemini 提出的 PowerShell 操作不會直接取得 PowerShell 專用解析能力。
- `PermissionPolicy.Validation.cs` 的預核准驗證只接受相同程式、完整參數、工作目錄及單一 literal invocation。`cd backend; dotnet test` 與在 backend 執行 `dotnet test`，不會被當成同一授權。

**影響：**即使都是讀取副本內檔案，變數、迴圈、動態路徑、Shell wrapper 或額外參數仍會人工確認。這不是單純「設定沒有保存」。

**建議：**優先讓 agent 使用結構化檔案工具，以及 `{ executable, argv, cwd, profileId }` 驗證工具，避免把每件事都表達成 Shell。Shell 類型由可驗證的轉接層／程序資訊提供，不採信模型自己宣稱。可辨識但格式不支援時，回傳具體原因與受支援形式，讓 agent 重新提出等價操作，再重新驗證；越界／明確拒絕不允許靠改寫繞過。

**驗收：**各 CLI 的代表性讀取、修改、搜尋、建置皆有真實協定 fixture；拒絕結果包含穩定原因碼，而非全部顯示未知指令。

### A4．大量搜尋會把依賴目錄算入 20,000 項上限（P2，已確認）

`PermissionPolicy.cs:168` 的 ReadSet 遞迴列舉檔案／目錄，不依 rg 的 ignore 行為排除 node_modules、bin、obj；超過 20,000 項或遇到 reparse point 即要求確認。

**影響：**安裝依賴後，相同的根目錄搜尋可能從自動允許變成人工確認。即使 rg 本身會略過部分目錄，權限預檢仍可能先擋住。

**建議：**明確建模實際搜尋工具與選項的讀取範圍；先鼓勵指定 src／tests 等搜尋根，提供超限目錄診斷。不能僅硬編碼忽略 node_modules，否則遇到 `--no-ignore`、跟隨連結等選項會破壞邊界一致性。

### A5．自動化模式不使用舊允許規則，且確認有累計上限（P2，已確認）

`SqliteTaskStore.Permissions.cs:33` 在 AutomationEnabled 時直接不查詢舊 ToolPermissionRules；人工確認累計到 50 次會拋出 ConflictException。未知操作只能單次允許。

**影響：**使用者可能以為舊規則能排除重複確認，但自動化模式下不生效。長任務即使每次都核准，也可能因累計上限中斷。

**建議：**介面清楚顯示生效的政策層級與停用規則。以「明確命令設定＋參數＋cwd＋用途＋設定版本」建立受控能力，不開放任意 prefix 永久授權。達到確認預算前先通知，並統計重複原因。

## 優先修正：建置與流程

### B1．後端驗證／預覽預設值寫死另一個專案（P1，已確認）

`frontend/src/components/ProjectExecutionFields.tsx:15` 新增後端測試時使用 `backend`＋`dotnet test CHR.sln`；新增後端預覽使用 `CHR.API/CHR.API.csproj`。

**影響：**不符合 CHR 結構的專案，照預設儲存即可在執行時失敗。

**建議：**辨識 `.sln`／`.slnx`／`.csproj` 與 package scripts，讓使用者選擇；無法辨識則保持空白、要求填寫。儲存前驗證目標存在，提供明確的「測試此設定」。避免把特定範例當可直接執行的預設值。

### B2．一般建置／測試失敗沒有有界自動修復循環（P1，已確認）

`Execution.cs:85–98`、`Execution.Workflow.cs:53–65` 在 agent 一次執行後驗證，失敗直接拋例外；Baseline 失敗也直接結束。雖然部分 AI 審查有重試，並不等於 build/test 失敗可自動修復。

**建議：**實作「驗證 → 結構化錯誤 → 同一 worktree 修正 → 再驗證」，限制次數、時間與重複錯誤；區分環境缺失、程式編譯錯誤、測試失敗與權限拒絕。Baseline 本來就失敗時應進入環境診斷／明確核准的基準修復模式，不把既有失敗當 TDD Red，也不無條件改變測試。

**驗收：**注入一次編譯錯誤能修正後通過；持續相同錯誤會停止並保留診斷；權限拒絕不透過重試繞過。

### B3．環境準備與驗證耦合，錯誤摘要容易漏重點（P2，已確認）

`DotnetValidationRunner.cs:25–37` 每次驗證都執行 PrepareArguments，而且準備與驗證共用 timeout。`:45` 摘要只取 stderr＋stdout 的前 8 個非空白行。前端預設也未啟用依賴準備。

**影響：**新 worktree 缺少 npm 依賴時建置失敗；勾選 npm ci 後每次驗證又重新安裝。下載耗時占掉測試期限；重要編譯錯誤若在後面，介面摘要只剩啟動／還原訊息。

**建議：**獨立 EnvironmentReady 階段，依 lockfile、工具版本與 worktree 狀態判斷何時重做準備；準備與驗證各自 timeout／日誌。保留完整 stdout/stderr artifact，摘要提取錯誤碼、檔案行號與尾端資訊；逾時也保存已產生的輸出。專案設定增加 SDK／Node／CLI 路徑與版本預檢。

### B4．人工回覆後，後續步驟可能使用錯誤基底（P1，程式碼可確定的條件式缺陷）

`SqliteTaskStore.Workflow.cs` 的 ContinueWorkflowAsync 遇到 `⚠️` 開頭摘要時，移除最後完成步驟，並把該步驟 ResultCommit 放進 RevisionCommit；但 `Execution.cs:50` 選基底時優先使用剩下的 StepResults 最後一筆 commit。

**重現條件：**A 完成於 commit A，B 完成於 commit B 但需人工回覆；回覆後留下 A 的 StepResults，RevisionCommit=B。下一輪實際從 A 開始，B 已做好的變更沒有被當作續修起點。若是第一步發生，沒有 A 才會使用 B。

**建議：**使用明確 ResumeCheckpoint／ResumeReason，不依摘要 emoji 決定狀態；明確保存需要續修的 commit 與步驟。新增真實 Git 的第二步人工回覆回歸測試，檢查檔案內容與 CreateAsync 的基底，不能只檢查 agent 呼叫次數。

### B5．AI 監督分支有放行漏洞與證據不一致（P1，已確認）

- `Execution.Workflow.cs:87–89` 超過 120,000 字元的監督 diff 直接回傳 Pass；獨立 Review 路徑卻會回 Uncertain。
- 監督結果只處理 ResolvedWithinRules、NeedsUserConfirmation／Uncertain，沒有白名單驗證。其他字串可落到一般完成路徑。
- 規則內修正後 `:104–108` 只驗證 exit code／總數／失敗數，沒有重新核對 baseline／Red 的測試 ID，也沒有再次取得監督通過結論。

**建議：**結果只能接受明確 enum，未知／缺失一律不可通過；超長 diff 分批審查或明確轉人工。所有修正路徑使用同一驗證門檻，保留原測試集合與每輪證據，必要時再次審查。

**驗收：**超長 diff、無效 verdict、修正時刪除既有測試，均不能被標為完成驗收。

### B6．自訂 Review 與舊 Review 的重試行為不一致（P2，已確認）

`Execution.Workflow.cs:153` 對 NeedsChanges 直接拋例外，導致 run failure；`SqliteTaskStore.cs:152` 的 correction 只在成功到達 AwaitingReview 時才考慮 MaxReviewRetries。

**影響：**自訂 Review 步驟要求修改時，不會使用同一套 MaxReviewRetries 自動修正邏輯。

**建議：**共用一個有界的 Review→修正→驗證→再 Review 狀態機；在設定介面顯示適用範圍。

## 其他值得改善的部分

### C1．測試數量足夠，但關鍵端到端路徑尚未成為固定門檻（P2）

現有大量單元／整合測試是優點。`scripts/dev.test.mjs` 的真服務啟停預設略過；`backend/tools/DevFlow.LiveCheck` 使用直接 Codex runner，不是目前所有 provider 共用的 RoutedCliRunner／PermissionProcess 路徑。本次檔案盤點未找到版本庫內 CI YAML。

建議建立不消耗模型的可控 CLI 測試程序，走正式轉接器與 API／Worker：規劃、核准、讀寫、權限等待與回覆、一次 build 失敗修復、Review 退回、續跑、merge。再針對真實 CLI 建立使用者明確觸發的相容性 smoke，記錄版本。CI 加入 frontend build/test、完整 .NET build/test、launcher runtime 與重要權限回歸。

### C2．權限查詢成本隨歷史成長（P2）

每個等待中的請求每 200ms 呼叫 ListToolApprovalsAsync，讀回整個 task 的歷史並逐筆反序列化，且使用交易。增加 API 的 request ID 單筆查詢、Pending 索引與事件通知／退避輪詢；歷史分頁。並行能力擴充前先處理這項，避免把一個等待變成大量 SQLite 工作。

### C3．Worktree 預設位置不適合讓 DevFlow 開發自己（P2，條件式）

`scripts/dev.mjs:12`、`RuntimePaths.cs` 的開發預設 worktrees 位於 DevFlow repository 內的 `backend/src/DevFlow.Worktrees`；`GitWorkspaceManager.CreateAsync` 禁止 worktree root 位於被管理 repository 內。

管理其他 repository 時未必有問題；若將 DevFlow 自己登錄為任務專案，預設路徑會被拒絕。建議預設改為 repository 外的使用者資料根目錄，並在專案登錄時顯示實際 worktree root 與衝突。

### C4．合併與恢復能力有清楚但有限的範圍（P2，設計限制）

GitMergeService 使用 fast-forward only；主分支在任務期間前進就可能無法合併。Worker 重啟會將中斷 run 記為失敗，沒有自動重連舊 CLI。失敗步驟的未提交變更保留在舊 worktree，重試則依 commit 建立新副本。

建議提供「更新至最新目標 → 在新隔離副本整合 → 重驗證 → 重審核」流程，以及明確的失敗副本檢視／選擇恢復操作。不要自動 force merge，也不要把未知狀態的孤兒程序視為已停止。

### C5．文件與生效架構不一致（P2）

backend README 仍描述 Claude restricted、不提供 Bash、尚無即時 stdout 等舊行為；PermissionProcess 的正式路徑會移除 restricted、加入 Bash 與雙向確認。根 README 又累積大量不同次權限修補說明。

建議文件分成：快速啟動、權限模型、各 CLI 能力矩陣、流程恢復、診斷。明確顯示三層：DevFlow 操作政策、CLI 原生政策、OS 權限。UI 直接顯示本次命中哪一層，而非統稱權限問題。

## 建議落地順序

1. **先消除「無聲卡住」：**開發版全域待確認清單、通知、阻塞原因碼、等待時間；修掉 CHR 預設與續跑基底／審查放行缺陷。
2. **再消除「正常操作反覆核准」：**結構化工具、可靠 Shell metadata、可測試的驗證 profile 能力與解析失敗診斷；保留越界和未知副作用的確認。
3. **補上「建置失敗後自己修」：**環境預檢、準備快取、有界修復循環、完整錯誤與 checkpoint。
4. **最後提升吞吐與可靠性：**有界並行、repository 互斥、事件推送、查詢分頁、正式路徑端到端測試、分歧整合。

不建議把工作目錄在專案內等同於允許任意腳本。任意程式仍能存取副本外、網路與憑證；若產品要承諾任意程式都不越界，必須由 OS／容器等實際隔離提供能力，不能只靠命令字串推論。

## 另一台主機需要的最小證據

針對一個失敗 Run 與一個卡權限的 Run 收集即可，不需先搬整套資料：

- DevFlow commit、Node／.NET SDK／AI CLI 版本、CLI provider。
- 任務與 Run ID、流程步驟、驗證設定與是否 TDD。
- 權限請求的 tool、完整 command、cwd、shell metadata、risk reason、policy version；先移除密碼／token。
- 該 Run 的 command.json、stdout.log、stderr.log、evidence.json，以及 API／Worker 時間相近的啟動器日誌。
- 使用預設 npm run dev 時，日誌位於 `backend/src/DevFlow.Api/.data/dev-logs`，artifacts 位於同一資料目錄下；若設定 DevFlow__DatabasePath／ArtifactsRoot，依實際值為準。

這些資料可用來判斷具體是錯誤專案路徑、缺依賴、原生 CLI 擴權、解析能力不足，還是實作本身編譯失敗。以上改善可先依程式碼證據進行，不必等所有事故都收齊。
